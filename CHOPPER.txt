tcp_tso_chop(): a software TSO splitter KPI - work plan
=======================================================

Living plan, started 2026-08-27.  Companion to TSO.txt (the
if_pair TSO work) and the offload cluster in NOTES.md, which
holds the analysis this plan executes: the closing-synthesis
target architecture, the sfxge precedent (the in-tree splitter,
wrong interface), the custody analysis (why the balk sites and
driver transmit paths are the right callers), and the tso_wrap
prototype whose tw_chop() is the working core of the function.

Objective
---------

One in-kernel function that splits a CSUM_TSO-marked mbuf chain
into wire-ready segments, serving two consumer classes:

  - forwarding balk sites (ip_output/ip6_output EMSGSIZE, both
    tryforwards, ip6_forward, pf_route): split transit frames
    when the egress lacks hardware TSO - "Phase A" of the GSO
    analysis, which removes the routed-TSO stall, lifts
    if_pair's default-off restriction, obsoletes
    patches/routed-tso-forwarding.patch (exemption becomes
    handler), and makes router-safe LRO possible;
  - drivers without hardware TSO: advertise IFCAP_TSO honestly
    and call the chopper in their transmit path - upgrading the
    survey's "software endpoints and tunnels: no TSO" column
    (gif/gre/wg/ovpn inner-chop-then-encap; legacy NICs;
    tso_wrap shrinks to advertise-and-call).

Both Ethernet-framed and bare-L3 callers are supported by a
single l2hlen parameter: link headers are opaque replicated
bytes (same MACs/ethertype/VLAN tag every segment), so Ethernet
support is "copy l2hlen more bytes, parse IP at the offset".
Worst-case header 14+4+60+60 = 138 bytes fits one pkthdr mbuf.

API sketch (final form decided in P1):

  int tcp_tso_chop(struct mbuf *m, struct mbuf **chain,
      u_int l2hlen, int flags);

  - Contract modeled on ip_fragment(): consumes m on success,
    returns segments as an m_nextpkt chain for the caller's
    send loop; frees everything and returns errno on failure;
    M_NOWAIT only (callers hold epoch/locks).
  - flags: TSO_CHOP_HWCSUM (keep per-segment request bits +
    pseudo-header th_sum) vs software checksums (the
    in_delayed_cksum pattern); room for future TSO_CHOP_*.
  - Per segment (the tw_chop/sfxge arithmetic): th_seq advance;
    v4 ip_len + INCREMENTING ip_id / v6 ip6_plen; FIN|PSH kept
    last-only, CWR first-only; v4 header csum always computed;
    payload attached by m_copym reference, headers copied;
    m_dup_pkthdr preserves flowid/fib/tags for queue steering.

Non-goals (decided in NOTES.md; do not relitigate silently):
GRO/merge (driver rx loops own the batch boundary), LRO reversal
(formally optional; chopper is sufficient), UDP/SCTP (boundary
semantics), IPv6 extension headers (stack excludes them from TSO
anyway), VXLAN-inner splitting (needs the encap-aware variant;
explicit scoping decision when someone needs it), per-route TSO
control (RTF_NOTSO idea parked).

Risks / open questions
----------------------

- M_EXTPG + software checksum is the main correctness risk; P1
  resolves it by verification or explicit rejection.
- Converted LRO aggregates arrive as ~44-mbuf chains; when the
  chopper's OUTPUT feeds a hardware-TSO NIC instead (P3 fast
  path) the segcount reconciliation stays with iflib's m_defrag.
  The chopper itself emits 2-mbuf segments (header + shared
  cluster refs) - always within limits.
- Performance target: chop cost at or below ip_fragment() for
  equal output; anything worse needs explaining before P7.
- Review risk: the P3 semantics change (balk -> handler) touches
  hallowed paths; the fallback position is KPI + driver callers
  only (P1/P4/P5 stand alone) with P3 as a follow-up RFC.
- After upstreaming: tso_wrap and lro2tso remain as demos for
  older systems; note their supersession in their headers.

Effort summary: roughly a week of focused work to the end of P6;
P7 is calendar time, not effort.
